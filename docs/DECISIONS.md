# Decisions

A short log of technical decisions: what we chose, why, and when. Newest at the bottom.

| Date | Decision | Why |
|---|---|---|
| 2026-11-11 | **Phaser 4** for the client, code-first (not an editor-based engine) | It's a TypeScript framework you call from code, so it fits a .NET/Angular workflow. v4 is the current major version, and starting on v3 would mean migrating later. |
| 2026-11-11 | **Server is the referee.** All rules live in pure C# (`Tactics.Core`). | One source of truth, no client-side cheating, and the same inputs always give the same outputs. That makes replays and tests possible. |
| 2026-11-11 | **.NET 10 LTS** rather than .NET 11 | Both are supported until November 2028 (STS releases now get 24 months). The ecosystem is still catching up with 11: Npgsql's EF Core 11 provider is a release candidate. |
| 2026-11-11 | **Aspire** for local orchestration | One command starts the API and the client. The dashboard shows logs and traces, and URLs are injected, not hard-coded. It replaces docker-compose plus manual ports. |
| 2026-11-11 | **PostgreSQL** for persistence (from Step 12) | Free, open source, and has a first-class EF Core provider (Npgsql). It runs as a container in Aspire and Testcontainers. Same major version everywhere. |
| 2026-11-11 | Solution file is **`Tactics.slnx`** | The XML format is the .NET 10 default. It's short, readable and gives clean diffs. |
| 2026-11-11 | **`TreatWarningsAsErrors` on every project**, tests included, plus `EnforceCodeStyleInBuild` | The build check requires 0 warnings anyway. xUnit's analyzers catch real test mistakes, such as a missing cancellation token. |
| 2026-11-11 | AppHost health-checks the API on its **`http` endpoint** | With an untrusted HTTPS dev certificate (fresh machine, CI), the https probe failed. The API stayed "Unhealthy" and `WaitFor` blocked the client forever. |
| 2026-11-11 | The Vite proxy prefers **`API_HTTP`** over `API_HTTPS` | The browser → Vite → API hop stays on localhost, so plain http avoids dev-certificate problems. `secure: false` covers the https fallback. |
| 2026-11-11 | **TypeScript 7** (native compiler), with `strict: true` written explicitly | It's what create-vite 9 scaffolds. Writing `strict` explicitly documents the rule from `CLAUDE.md`, whatever the compiler's default. |
| 2026-11-11 | Vite `chunkSizeWarningLimit: 1500` | Phaser alone is ~1.4 MB minified (~360 kB gzipped). The limit sits just above it, so growth in our own code still warns. Splitting Phaser into its own cached chunk can wait for deploy polish. |
| 2026-11-11 | Tab title set at runtime (`document.title = GAME_TITLE`); `<title>` in `index.html` stays empty | It keeps the title in exactly one place in code. Trade-off: static HTML (link previews) sees no title. Revisit at Step 14. |
| 2026-11-11 | Network code lives outside Phaser (`client/src/net/`), with an injectable `fetch` | Vitest can test it without a canvas or a real server, much like constructor injection in .NET. |
| 2026-11-11 | Core namespaces follow folders: `Tactics.Core.Model`, `.Content`, `.Serialization`; `GameEngine` sits at the root | Conventional .NET layout. Later steps add rule folders next to them without one flat namespace growing forever. |
| 2026-11-11 | Content is parsed into **file DTOs** (nullable fields, enums as strings), then mapped to domain records | A missing field becomes "is missing", not a silent 0. A typo in `owner` gets a clear message instead of a parser exception. Same idea as model binding plus validation in ASP.NET. |
| 2026-11-11 | `ContentLoader` reports **every** problem at once, each as a `ContentError` with a stable **code** and a message | You fix all mistakes in one pass. Tests check codes, so messages can improve without breaking tests. This mirrors the rule-violation codes coming in Step 2. |
| 2026-11-11 | Stat minimums: `maxHp`, `power`, `move`, `minRange`, `maxRange` at least 1; `defense` at least 0; each side needs at least one unit | The plan's own Mage has defense 0. A side with no units would start an already-won game. |
| 2026-11-11 | Unknown JSON properties in content are ignored; enum names are case-insensitive | You can add your own notes fields. A typo in a required field still shows up as "missing". |
| 2026-11-11 | Rule tests use fixed stats (`AsciiBoard.DefaultUnitTypes`); real-content tests check validity only | Balancing `content/units.json` never breaks a test, but a broken file always does. Verified by rebalancing a copy: 69/69 still passed. |
| 2026-11-11 | `TacticsJson` sets `TypeInfoResolver` explicitly instead of relying on the host's default | .NET 10 single-file apps (and Native AOT) switch reflection-based JSON off by default, and the options crashed there. Core shouldn't depend on its host's settings. |
| 2026-11-11 | Core removes the `System.IO` and `System.Net.Http` implicit usings | It's a visible reminder that Core does no I/O. Reading files belongs to the tests and the API. |
| 2026-11-11 | **`ActionOutcome`**, not the plan's `ActionResult` | `ActionResult` is also an ASP.NET Core MVC type. An API file that imports both namespaces gets CS0104 "ambiguous reference", and readers would take it for the MVC type. |
| 2026-11-11 | `ActionOutcome` is a **closed hierarchy**: a private constructor and two nested records, `Accepted` and `Rejected` | An action has exactly two outcomes, and no other code can add a third. C# 14 can't prove the list is complete, so a `switch` on it still needs a `_` arm. |
| 2026-11-11 | `TacticsJson` sets **`AllowOutOfOrderMetadataProperties = true`** | System.Text.Json otherwise reads `"type"` only as the first property. PostgreSQL `jsonb` reorders keys (shortest first), so a stored move would fail to load in Step 12. The cost is extra buffering, only when `type` isn't first. |
| 2026-11-11 | New Core folders `Actions/`, `Events/`, `Rules/`, with **one file per family** (`GameAction.cs` holds every action type). `ActionOutcome` and `RuleViolation` sit at the root, next to `GameEngine`. | Namespaces keep following folders. One file per family shows every case and its `[JsonDerivedType]` line together, like a TypeScript union type. The root holds the engine's contract: what you call and what you get back. |
| 2026-11-11 | `GameEngine` is a **`partial` class**, with one file per action's rules (`GameEngine.Move.cs`; Act and Turn follow in Steps 3–4) | One entry point to call, without one huge file. Shared helpers (`Reject`, `Describe`, `Tiles`) stay in `GameEngine.cs`. |
| 2026-11-11 | `Pathfinding.Reachable` is **geometry only**: it ignores the turn, `HasMoved` and `HasActed` | Who may move is the engine's rule. Step 4's available actions reuse the same search. |
| 2026-11-11 | `ReachMap` is a **class**, not a record | It hides its came-from table behind `CanReach` and `PathTo`. A record's equality would compare that table by reference anyway. |
| 2026-11-11 | **`AlreadyActed` is checked before `AlreadyMoved`** | From Step 3, acting sets both flags. Then "already acted" is the real reason the unit can't move, and Step 3's tests expect that code. |
| 2026-11-11 | Core JSON keeps System.Text.Json's **default property order**, so `player` comes last: `{"type":"move","unitId":…,"to":…,"player":"one"}` | It writes a subtype's own properties before inherited ones. Readers match properties by name, so an ordering attribute would only be cosmetic. |
| 2026-11-11 | Board-picture tests compare with **`ignoreLineEndingDifferences: true`** | With `core.autocrlf=true`, a Windows checkout turns the line endings of a test's raw string into `\r\n`, while `AsciiBoard.Draw` writes `\n`. |
| 2026-11-12 | **`CalculateHeal(healerType, targetType, targetHp)`**, not the plan's `(healerType, target)` | `Unit` has no `MaxHp`: it lives on the target's `UnitType`. Formulas take stats and numbers, never the board or the state. |
| 2026-11-12 | Act checks run **who → what → where**: the actor exists, is yours and hasn't acted; the target exists; then the right kind (`InvalidTarget`); then the range (`TargetOutOfRange`) | Same shape as a move, with geometry last. The wrong kind of target never works this turn, while a target that's too far may work after a move, so the message names the deeper problem. |
| 2026-11-12 | **Overkill:** `UnitDamaged.Amount` is the formula's full damage; `HpAfter` stops at 0 | A pop-up shows how hard the hit was, the usual game convention. `HpAfter` already gives the real HP, and `CalculateDamage` keeps the plan's stats-only signature. |
| 2026-11-12 | `Combat.cs` holds **only the two formulas**. The 0-HP floor and the range rule live in `GameEngine.Act.cs`. | `Combat.cs` is the balance knob. The floor is what HP means, and range is a targeting rule, like walkability in `Pathfinding`. |
| 2026-11-12 | `CheckTarget` returns the rejection (code and message) or `null`; Step 4's available actions will call it | One function decides and explains, so the targets the client highlights are exactly the ones `Apply` accepts. Same idea as reusing `Pathfinding.Reachable` for moves. |
| 2026-11-12 | `ApplyAct` **reads the target again** after marking the actor as spent | Records are snapshots. If a unit ever targets itself (a heal with `MinRange` 0), its old copy is no longer in the list, and `Replace` would throw. One lookup prevents that, and a test guards it. |
| 2026-11-12 | Act test boards keep **a unit on each side** after every action | Step 4 checks for victory after each action. A board that loses a side would then get an extra `GameWon` event, and these exact event lists would break. |
| 2026-11-13 | `GetAvailableActions` lists **only units that can still move or act** | On your turn, an empty list then means "only End Turn is left", which the Step 8 HUD and a future AI can use as is. A unit with no entry is spent (approved in the Step 4 brief). |
| 2026-11-13 | The win condition lives alone in **`Rules/Victory.cs`** (`WinnerOf`). One last step in `Apply` (`FinishIfWon`) applies it after **every** accepted action. | One place for win conditions, like `Combat.cs` for formulas. No action's rules can forget the check, and rules such as "survive N turns" or "hold a tile" only need the state. |
| 2026-11-13 | `WinnerOf` **throws** when both sides have no units | v1 has no draws, and no action removes two units. A silent `null` would leave a game with no units running forever. The exception names the one place to decide what it means. |
| 2026-11-13 | `EndTurn` refreshes **only the next side's** units (the plan's rule) | Refreshing the side that just played would play the same. This way the screen can still show which units acted during the other turn. A test pins the choice. |
| 2026-11-13 | `Replay` throws **`ReplayException`** with the action, its **sequence** (from 1) and the rule **code** | A log that doesn't replay is a bug, not a player's mistake, so it's an exception, unlike `Apply`'s `Rejected`. Tests check the sequence and code, so the message can change. |
| 2026-11-13 | **Command sourcing trade-off:** a log replays through the *current* rules | A rule change (in `Combat.cs`, say) can make a stored game replay differently, or throw. Harmless while games live in memory (Step 5). At Step 12, propose storing a rules version with each game. |
| 2026-11-13 | Tests compare states **as JSON** (`StateJson`), not with `Equals` | Records compare `ImmutableList` by reference. JSON covers every field, future ones too, with no comparer to maintain. Both states must come from the same setup (hash-set order). |
| 2026-11-13 | A **reflection guard test** checks that every action and event type has `[JsonDerivedType]` and a round-trip sample | A missing attribute only fails at run time: System.Text.Json throws when it writes the type. Checked by removing `GameWon`'s line: 3 tests failed, the guard among them. |
| 2026-11-13 | A **brute-force test** compares `GetAvailableActions` with `Apply` on 5 game moments: both sides, every unit, every tile, every target | Highlights and the referee must never disagree. It proves the reuse of `Reachable` and `CheckTarget`, and catches a rule later added to only one of them. |
| 2026-11-13 | **`TacticsJson.Configure(options)`** in Core applies the JSON conventions to any options; Core's `Options` and the API's HTTP options (`ContractJson`) both use it | The wire format and Core's JSON are defined once, so they can't drift apart. It's pure code, so Core stays BCL-only. |
| 2026-11-13 | The API **reads requests strictly**: required fields, nullability, and numbers as JSON numbers (`ContractJson`) | A forgotten `expectedSequence` would otherwise read as 0, and a missing `unitId` as null. Strict numbers also make the OpenAPI schema say `integer`, not `integer or string`. |
| 2026-11-13 | A **contract modifier** makes an action without `"type"` a `JsonException` | System.Text.Json throws `NotSupportedException` for the abstract `ActionDto`, and ASP.NET Core answers 500: a client's mistake looked like a server bug. Now it's a 400, like an unknown `type`. |
| 2026-11-13 | **`UseExceptionHandler` runs outside Development only** | Inside Development it caught `BadHttpRequestException` before the developer exception page did, and turned every malformed request into a 500. `ProductionErrorTests` checks the production answers. |
| 2026-11-13 | Repository writes are **compare-and-swap** (`TryJoinAsync`, `TryAppendAsync` return false), with one `Lock` per game held only to check and write | Replays and rules run outside the lock, so games never wait for each other. A Step 12 primary key keeps the same promise. Checked: without the lock, the race tests failed in 3 of 3 runs. |
| 2026-11-13 | `GameService` returns **`ServiceResult<T>`** (errors as values); `ApiProblems.From` maps each `ServiceErrorKind` to one HTTP status | Same idea as Core's `ActionOutcome`. The service knows nothing about HTTP, so Step 11's SignalR hub can reuse it. |
| 2026-11-13 | Check order: **game (404) → token (401) → sequence (409) → rules (422)**; a join checks the code (403) before the seat (409) | A stranger learns nothing about the game. A rule verdict on a view the player hasn't seen means nothing, so the stale view is reported first. Tokens belong to one game, so 401 needs the game: ids aren't secret. |
| 2026-11-13 | Tokens: **32 random bytes, base64url, stored as SHA-256**, compared in constant time. Invite codes: **8 characters** without look-alikes, case-insensitive | A fast hash is enough for a random 256-bit secret; slow hashes exist for guessable passwords. People type invite codes, so 0/O and 1/I/L are out and case doesn't matter. |
| 2026-11-13 | DTOs **reuse Core's enums** (`PlayerSide`, `GameStatus`, `Ability`) but **map every record**. Guard tests check that the DTOs list Core's `type` names and keep each event's JSON | Enums are shared vocabulary with stable camelCase names. Records go through `ContractMapping`, so a Core rename can't silently change the wire. |
| 2026-11-13 | API tests run on a **fixed `TestScenario`**, swapped in with `ConfigureTestServices`. One smoke test uses the real `content/` | Same rule as Step 1: balancing `content/` never breaks a test, but broken content still fails one. |
| 2026-11-13 | Game ids are **`Guid.CreateVersion7(time.GetUtcNow())`**; only `GameService` reads the clock (`TimeProvider`) | Time-ordered ids keep Step 12's index appending at the end. Tests set the time with a `FakeClock`, so no hidden `DateTime.Now`. |
| 2026-11-13 | `GameService` is **scoped**; the repository and `SetupProvider` are singletons. Content loads **at startup**, not on the first request | Step 12's EF repository will be scoped (one `DbContext` per request). Broken content stops the API at once, with every problem listed. |
| 2026-11-13 | **Scalar** with telemetry, its AI agent and MCP **turned off**; the OpenAPI document marks only the two token endpoints | It's a local dev tool, so nothing should leave the machine. An endpoint-level transformer (`WithPlayerToken`) lets Scalar send the token where it's needed. |
| 2026-11-13 | Every **401 carries `WWW-Authenticate: Bearer`**, added in `CustomizeProblemDetails` | RFC 9110 requires the header on a 401. One hook covers every 401, wherever it comes from. |
| 2026-11-13 | **One PLACEHOLDER file**, `client/src/media/placeholder.ts`: theme colours, sizes, generated textures and the unit letter. `config.ts` keeps engine and layout numbers | CLAUDE.md's art rule wants every placeholder visual in one file. Step 9 then replaces one file's job (approved in the Step 6 brief). |
| 2026-11-13 | **Team colours by tint**: one white unit texture, tinted per side (MULTIPLY, Phaser 4's default tint mode), not one texture per team | Both teams share a texture, and the step teaches tint. Watch out in Step 8: a hit flash in `TintModes.FILL` must restore MULTIPLY and the team colour after. |
| 2026-11-13 | The board's **layout is computed** (`layoutBoard` centres any board size), and `BoardRenderer` owns it as `layout` | The board's size comes from the scenario, so a fixed origin would only centre 8×8. Units, and clicks from Step 7, read one layout. |
| 2026-11-13 | **Pure client modules never load Phaser** (`grid`, `reconcile`, `unitDisplay`, `net/*`, `debugCommands`); `placeholder.ts` only uses `import type Phaser` | Phaser touches `window` as it loads, so Vitest (Node, no DOM) couldn't import them. `import type` disappears from the JavaScript. |
| 2026-11-13 | `ApiClient` **trusts success bodies, reads error bodies defensively**, and turns "no answer at all" into `ApiUnreachableError` | The API is ours, and both sides pin its JSON. Errors can come from a proxy (plain text, HTML). A separate type keeps a real `TypeError` bug from reading as "can't reach the server". |
| 2026-11-13 | `ApiClient`'s default `fetch` is **wrapped in an arrow function** | Called as `this.fetchFn(...)`, the browser's own `fetch` gets the ApiClient as `this` and throws "Illegal invocation". |
| 2026-11-13 | **Dev-only console commands** (`window.tactics`, `game/debugCommands.ts`) behind `import.meta.env.DEV` | Without input, nothing could change the screen before Step 7. Production bundles drop them: checked, 0 matches in `dist/` (approved in the Step 6 brief). |
| 2026-11-13 | **Only the unit's body breathes**, computed from `time` (not `delta`) in `GameScene.update` | A function of time is frame-rate independent. The container's own scale stays free for Step 8's tweens, which a per-frame write would overwrite. |
| 2026-11-13 | Scene keys are a **`static readonly KEY`** on each scene class | No scene name is typed twice, so a typo is a compile error, not a "scene not found" at run time. Like `nameof` in C#. |
| 2026-11-13 | Local mode keeps **both tokens in memory only**, and plain `/` keeps the Step 0 screen with a hint | Step 10 brings `localStorage` sessions and the menu. Until then, a reload starts a new game, which is fine for pass and play. |
| 2026-11-13 | `GameScene` **ignores late answers after it shuts down** (a `running` flag set on `SHUTDOWN`) | A request can outlive its scene (a restart, Step 10's menu). Drawing into a stopped scene would throw. |
